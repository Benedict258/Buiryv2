Format: what is assumed, source, how to verify, what changes if false. Starting list is Architecture section 19 (A1-A12). Status values in the register table: `confirmed` (docs or a live check agree), `wrong-and-fixed` (contradicted, and the code now follows reality), `open` (not yet settled), `withdrawn` (no longer relevant).

## Step 0 status

The live documentation was read on 2026-10-28 (results in "Step 0 results" below). The `Status` column in the register table further down summarises the results table and the live checks. "Confirmed (docs)" means a documentation page or the vendor SDK source says so; nothing is "verified" until the matching live check in `LOCAL_CHECKS.md` has run.

**Chain transport (A8): gRPC only.** Tatum's documented Sui JSON-RPC hosts return 404 (checked 2026-10-28, mainnet and testnet, with a control call proving the key works), so chain checks run over gRPC only. When gRPC is unavailable, rate limited or over budget, the result is `unknown` with `degraded: true`; it is never `pass`, and never reused from an expired cache entry (a current-object read is cached for 60 seconds, then dropped). `buiry doctor` and the Verification screen say this in plain words. A transaction digest is immutable, so a cached transaction result stays valid indefinitely. The JSON-RPC backend remains in code and is used only if `TATUM_JSONRPC_URL` is set; leave it unset until Tatum serves it again.

## Seal session scope (A26, read 2026-11-11)

- **Encryption identity** (`@mysten-incubation/memwal` 0.1.14, `dist/manual.js`, `sealEncrypt`; same in `packages/sdk/src/manual.ts` at https://github.com/MystenLabs/walrus-memory, branch main, which the old MemWal URL now redirects to): "id = hex(utf8(namespace)) || hex(ownerAddress[2:]) || hex(u64le(counter))". The account object id is not part of it.
- **Policy:** the SDK calls `<sealPolicyPackageId or packageId>::account::seal_approve(id, registry, account)`. Its comment: "`seal_approve` authorizes delegates at account scope, however, so this does not isolate delegates from each other's namespaces" and "every account delegate may request every namespace key". Docs (https://docs.wal.app/walrus-memory/fundamentals/concepts/ownership-and-access.md): "Delegate keys are not scoped to a namespace or a read-only subset of memory." and "An authorized delegate can access memories across every namespace in the account."
- **Key lifetime:** SDK comment: "SEAL hands out one reusable secret key per identity, so an id fixed at `owner` would let any delegate that ever fetched the key keep decrypting new memories forever"; the trailing `access_counter_version` exists so "a revocation bumps the counter, which changes the identity". Docs: "`seal_approve` rejects any counter above the account's current one".
- **Session:** Seal docs (https://docs.sui.io/sui-stack/seal/using-seal): a `SessionKey` is for "a specific package"; "the session key can be used to retrieve multiple decryption keys for the specified package"; "Seal evaluates the transaction as if the user sent it". TTL bounds come from code, not docs: `@mysten/seal` 1.5.2 `dist/session-key.mjs` rejects TTL outside 1 to 30 minutes and treats a session as expired 10 s before its TTL.
- **Not read:** the Move source of `seal_approve`. The repository has no contracts directory, so the policy is known from docs and SDK comments only.
- **What it means:** a Seal session from Buiry's delegate can obtain the key of every namespace in the account, which in managed mode is every tenant. The 5-minute TTL bounds key requests, not decryption: a key fetched in that window decrypts that namespace (past and future memories) until a delegate is removed. Caching one session for 5 minutes instead of building one per call does not widen this, because every session has the same reach; shortening the TTL (minimum 1 minute) narrows only the request window. Isolation between tenants needs separate Walrus Memory accounts or a self-hosted contract. Recovery after a leaked session or key is to remove (and re-add) a delegate, which raises the counter.
- **Conflict in the docs:** https://docs.wal.app/walrus-memory/relayer/self-hosting.md says "Walrus Memory isolates data strictly by **User (Owner address)** and **Namespace**"; the ownership page and the SDK say namespaces are not authorisation boundaries. Buiry follows the stricter reading.

## Seal session for recall (2026-11-10, Mainnet)

- **Source of the construction:** `@mysten-incubation/memwal` 0.1.14, file `dist/memwal.js`, methods `fetchServerConfig`, `buildSealSessionInner` and `buildSealSession` (also `packages/sdk/src/memwal.ts` in https://github.com/MystenLabs/MemWal). Steps: read `packageId` and `network` from the relayer's unsigned `GET /config`; `SessionKey.create({ address, packageId, ttlMin: 5, signer, suiClient })` with the delegate Ed25519 keypair; sign the personal message eagerly and `setPersonalMessageSignature`; `export()` and project `address, packageId, mvrName, creationTimeMs, ttlMin, personalMessageSignature, sessionKey` into a plain object; JSON, then base64; cache until TTL minus 30 s. `recall()` sends it on every call.
- **Helper versus own code:** the SDK exports no session helper (`buildSealSession` is a private method of `MemWal`), so using it would mean depending on a private method plus the same peer packages. Buiry builds the session itself with `@mysten/seal` 1.5.2 and `@mysten/sui` 2.38.0 (`packages/storage/src/seal-session.ts`), both pinned, both Apache-2.0, published by Mysten Labs maintainers, and at least two weeks old when added (1.5.4 and 2.39.1 were newer but only five days old). Verified live with exactly these versions.
- **The one Sui read:** `SessionKey.create` reads the package object and requires version 1 (`@mysten/seal` `dist/session-key.mjs`). Buiry injects that read from the chain gateway (`TatumGateway.getObject`), so storage opens no Sui network client. Ed25519 signature checks in `setPersonalMessageSignature` do not use the client.
- **Exported session contents:** `sessionKey` is the ephemeral session secret key. Buiry treats the exported session like a key: memory only, never logged, scrubbed from error messages.

## Live results for signed Walrus calls (2026-11-10, Mainnet)

- **A13 signing:** the relayer accepted delegate-key signatures for remember, bulk remember, job status, restore, stats and the Memory Read listing.
- **A3:** the delegate-signed Memory Read listing works for a third-party client.
- **A2:** a memory written through the public relayer on Mainnet got `end_epoch` 58 and an `expires_at` 210 days later (15 epochs of 14 days). Both fields were `null` for about the first 4 minutes after the write.
- **A23 (new), cause confirmed:** recall without a Seal session drops every candidate.
  - Symptom: `POST /api/recall` from Buiry's adapter answered HTTP 200 with `{"results":[],"total":0,"dropped_count":4,"degraded":true}` at 19:21Z, 19:22:48Z, 19:25:55Z and 20:02:32Z / 20:02:37Z (writes at about 19:20Z; `sort: recent` and `deadline_ms: 30000` made no difference).
  - Docs: "`dropped_count` only appears when at least one match dropped out because its blob download or decryption failed" (W-API). `degraded` is not documented on the relayer page; SDK `types.ts` says it is "True when one or more matched blobs were dropped". Recall "Returns decrypted plaintext results" (W-API). The header table lists `x-seal-session` as the "Seal SessionKey for relayer-managed decrypt flows" (W-API). What the relayer does when neither `x-seal-session` nor the deprecated `x-delegate-key` is sent is not stated.
  - SDK (`@mysten-incubation/memwal` 0.1.14, W-SRC): `recall()` always sends `x-seal-session`, built with `@mysten/seal` `SessionKey.create({ address, packageId, ttlMin: 5, signer, suiClient })` from the delegate key, with `packageId` and network from the relayer's `GET /config`.
  - A/B, same account, delegate and namespace: at 20:05:46Z the official SDK (sending `x-seal-session`) got HTTP 200 with `total: 4`, 4 results with text, no `degraded`, no `dropped_count`. Buiry's adapter, without the header, got all 4 dropped 3 minutes earlier.
  - Ruled out: index lag (vector search found all 4 matches in every call; `dropped_count` counts matches); blob availability (the SDK downloaded and decrypted all 4); account or namespace mismatch (our delegate public key is in `GET /api/accounts/{owner}/delegate-keys`, and that account id equals `WALRUS_ACCOUNT_ID`).
  - New account and delegate (owner's note): both were created the same day. The same new delegate recalls correctly with a session, so newness is not needed to explain the drops; whether it had any additional effect in the first minutes is unverified.
  - Also seen: intermittent connect timeouts to the relayer (`UND_ERR_CONNECT_TIMEOUT`, 10 s) on 2 of about 15 calls, behind the "fetch failed" errors; and one SDK recall that failed with "Unexpected status code: 404" before a retry succeeded (cause unverified).
  - Doc gaps: the SDK api-reference lists recall as returning only `results` and `total`, while `types.ts` also has `degraded` and `dropped_count`. The Memory Read listing "Returns metadata only, with no blob fetch or decryption" (SDK api-reference), which matches what we saw.
- **A6:** bulk of 3 items accepted; rate limits and per-item weight still not measured.
- **A23 fixed, live (23:44Z to 23:50Z):** with the Seal session the REAL contract recall returned the stored blob with exactly its text and no `degraded`; an acceptance run then recalled every listed memory in both contract namespaces (4 of 4 and 4 of 4) with text, with no `degraded` and no `dropped_count`. The package-version read went through the Tatum gateway on the documented mainnet gRPC host.
